A real-time Rust audio engine behind a SolidJS UI

26 November 2026 · file and line references are to commit b3a49c37

Synkopa is an open-source DAW. Its audio engine is Rust; its interface is SolidJS in a Tauri web view. The two halves have opposite needs: the audio callback has about 2.7 ms per block at 128 frames and must never wait, while the interface runs in a garbage-collected runtime that pauses when it likes. This is how they talk without either one stalling the other.

The rule, and what it rules out

The audio callback does not allocate, lock, or do I/O. That removes every ordinary way of sharing data: no mutex around the project, no Arc whose last reference might drop on the audio thread, no channel that allocates a node per message.

What is left is four one-way paths, each sized for what it carries.

Down: commands on a ring

The engine owns the project behind a mutex that only non-audio threads take. Anything the audio thread must know travels as a Cmd through a single-producer, single-consumer ring from the rtrb crate. The first thing the callback does each block is drain it:

fn drain(&mut self) {
    while let Ok(cmd) = self.cmds.pop() {
        self.apply(cmd);
    }
    // live keyboard events arrive on their own ring (the UI side never waits for a lock)
    ...

MIDI keyboard input gets a second ring, so a key press never queues behind a project edit that holds the engine lock.

A knob move is the common case, so it is the cheap one. Effect parameters are resolved to numbers on the non-audio side and sent by value:

pub const MAX_PARAMS: usize = 32;
/// Parameters of a built-in effect, already resolved to numbers on the
/// non-audio side. Fixed size so it travels through a ring buffer by value.
#[derive(Clone, Copy, Debug, Default, PartialEq)]
pub struct ParamBlock {
    pub values: [f32; MAX_PARAMS],
    /// EQ bands (unused slots have `on = false`).
    pub bands: [BandParams; 24],
}

crates/engine/src/processor.rs:146

That makes Cmd::Params a large enum variant, and Clippy says to box it. The comment above the enum explains why not: a box would have to be freed, and the thread that finishes reading it is the audio thread. The block is copied instead. Each processor then smooths its own continuous parameters per sample with a one-pole filter (about 20 ms for EQ gain), and faders ramp linearly across the block, so a jump in the message is never a jump in the signal.

Structure changes: build elsewhere, swap, send the old one back

Adding an effect or a track changes the shape of the mixer. The new graph is built on the calling thread, with all the allocation that takes, and arrives as Cmd::Graph(Box<Graph>). The audio thread does three things with it.

First it moves running processors across by effect id, so a reverb keeps its tail and a delay keeps its buffer when something else in the chain changes. Delay-compensation lines and fader ramps are carried the same way.

Then it swaps, and sends the old graph back:

let old = std::mem::replace(&mut self.graph, g);
self.trash(Garbage::Graph(old));
fn trash(&mut self, g: Garbage) {
    // The ring is sized generously; if it is ever full we leak rather than free here.
    if let Err(rtrb::PushError::Full(g)) = self.garbage.push(g) {
        std::mem::forget(g);
    }
}

crates/engine/src/rt.rs:1340, 1451

Freeing is as forbidden as allocating, so the old graph rides a second ring to a housekeeping thread that drops it. If that ring were ever full, the code leaks on purpose: a leak is a bug to fix later, while a free on the audio thread is a click now.

Up, slowly: the project as an event

The interface never edits its own copy of the project and hopes the engine agrees. It sends ops (putClips, putFx, setBpm and so on), and a batch is atomic by the simplest means available:

pub fn apply_all(p: &mut Project, ops: &[Op]) -> Result<Dirty, OpError> {
    let mut work = p.clone();
    let mut d = Dirty::default();
    for op in ops {
        d.merge(apply(&mut work, op)?);
    }
    *p = work;
    Ok(d)
}

crates/engine/src/ops.rs:1308

Undo is the same idea: up to 200 whole-project snapshots, not inverse operations. It costs memory and a clone per edit. In return, undo cannot drift from the edit it reverses, and the command line, which sends the same ops over a local socket, gets atomic batches and one undo step per command with no extra code.

After an edit the engine emits a state event with the project as JSON. On a large song that is close to 1 MB, which is fine once per edit and ruinous sixty times a second. So a drag is a gesture: the interface applies each step to its own copy at once, coalesces what it sends to one batch per animation frame, and the engine stays quiet until the gesture ends.

This is the unfinished part. A full-project event per edit is simple and has been easy to keep correct, but its cost grows with the song, not with the edit. Sending only what an op touched is the obvious next step.

Up, fast: one binary frame

Meters, the playhead and the spectrum in an open EQ window change every frame, and none of them belong in JSON. The audio thread publishes them without knowing whether anyone is listening: plain atomics for the playhead and CPU load, a peak per insert that the reader takes with swap(0), and for effects whose window is open, raw samples pushed into a small ring. If that ring is full, the audio thread skips the write.

A housekeeping thread wakes 60 times a second, reads the atomics, runs the FFTs for the watched effects, and packs everything into one little-endian frame. Tauri hands the bytes to the web view over a Channel with no JSON step:

#[tauri::command]
async fn telemetry_subscribe(app: St<'_>, channel: Channel<InvokeResponseBody>) -> R<()> {
    app.engine.set_frame_sink(Some(Box::new(move |bytes| {
        let _ = channel.send(InvokeResponseBody::Raw(bytes));
    })));
    Ok(())
}

Analysis is paid for only when someone looks: the interface tells the engine which effect windows are open, and only those get taps and FFTs (eight at most). The playhead in the frame is the beat being heard, the rendered position minus plugin delay compensation, so the line on screen matches the speakers.

The interface: reactivity for structure, a loop for motion

SolidJS updates the DOM node that depends on a value and nothing else, which suits a DAW's static structure: tracks, channels, effect chains. It is the wrong tool for sixty meter values a second. So telemetry never enters the reactive store. It lands in plain mutable objects, and one loop draws from them:

Only edges, such as play turning into stop, are written to the store. Everything that moves is canvas. Layers that depend only on parameters (an EQ's grid, a compressor's curve) are drawn once into an offscreen canvas and reused until their key changes. The playlist draws tiles larger than the view, shifts existing pixels on scroll, and paints only the newly exposed strip. Long lists build only the rows on screen.

The project in the store is updated by a keyed merge of what changed, so a component that holds a clip keeps the same object across edits.

Keeping the rule true

A rule about what a thread never does is only as good as its test. The engine's tests install a counting global allocator, arm it on the audio thread and on the worker threads, and play: 400 blocks, 8 synths, 8 insert chains, 4 threads.

let (_, allocs, threads) = play(4, 400, true);
assert_eq!(threads, 3);
assert_eq!(allocs, 0, "the audio thread or a worker allocated");

crates/engine/tests/rt_workers.rs:193

The same file checks that four threads produce output bit-identical to one. Independent chains run on a small pool whose dispatch is a few atomics: workers and the audio thread pull job indices from one counter, so if no worker wakes in time the audio thread does the work itself, and results are summed in a fixed order.

A callback that runs longer than its period is counted, as are the driver's own xruns, and the count travels in the telemetry frame.

None of the pieces here is new. Lock-free rings, graph swapping and deferred frees are how real-time audio has been written for decades. The useful finding is how little the web view costs once it is kept to its own side: it never holds anything the audio thread needs, and nothing that moves at frame rate goes through JSON or a reactive graph.
